# Keeping public and private editions together

1. Make operational changes in the complete private source and preserve its history and evidence.
2. Select the code or explanation needed to demonstrate the process publicly. Do not merge private history into this repository.
3. Replace property configuration with explicit local inputs or nonworking examples. Preserve the algorithm and document any behavior differences.
4. Compare source behavior, run the local regression cases, review links and examples, then scan the candidate files for secrets and private identifiers.
5. Review the staged file list and publish only the approved public edition.
6. Record the public commit and corresponding private source snapshot in the private source map. Keep sensitive evidence in the original private repositories.

## Differences in this public edition

- Booking sync has a configurable target calendar, a disabled default, and rejects an incomplete fallback stay rather than guessing three nights.
- Cleaning coverage has an example roster, disabled execution, generic owner naming, and an access-review reminder that contains no property-specific credential rule. The underlying 81-case decision suite is retained with sample identities.
- Monthly reporting has no hardcoded property/filer identity. It takes an explicit local JSON file and uses the currently reviewed official blank form contract. Filled field appearances use a standard PDF font to keep amounts readable across viewers; the signature stays blank. Source ledgers and completed forms are excluded.
- Four workflows have process-design guides rather than unverified claims of complete backend source.
- Existing public plugin and Airtable source stay in their original repositories, with direct links rather than duplicated packages.
